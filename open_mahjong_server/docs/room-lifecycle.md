# 房间生命周期与后台管理

房间用于入座、分队、准备和等待下一场；对局保存正在进行的牌局。两者分别由 `RoomManager` 和 `GameStateManager` 管理。退出房间、断开连接、结束对局和管理员关闭房间是四种操作，不能只删除某一份成员缓存来代替完整清理。

本次修复覆盖血战和血流双打结束后无法返房、离线座位残留的问题，并给 Web 平台管理员提供房间列表、创建与关闭入口。玩家房间面板布局及玩法选项不在此次调整范围内。

## 数据归属

| 数据 | 维护位置 | 用途 |
| --- | --- | --- |
| 房间配置、成员、房主、准备状态 | `server/room/room_manager.py` 的 `rooms` | 大厅房间的权威状态 |
| 固定座位、队伍、阵容版本 | `room_seats.py`、`room_teams.py` | 保持座位与成员列表一致，阵容改变后重新准备 |
| 当前连接 | `GameServer.players`、`user_id_to_connection` | 定位当前账号真正生效的连接 |
| 连接上的房间号 | `current_room_id` | 连接缓存；登录和断线时可由房间成员名单恢复 |
| 对局及玩家索引 | `GameStateManager` | 控制对局任务、断线接管、重连、观战和清理 |
| 房间实例与对局关联 | `instance_id`、`active_gamestate_id` | 防止旧对局清理或旧页面关闭同号的新房间 |
| 复式开闭室配对 | `sichuan_duplicate.py`、`PairedMatch` | 两桌同步、持久化进度、中断与整组删除 |

房间号允许后续复用，但运行中的对局仍保留号码占用。客户端、管理端不能只凭房间号认定是同一个房间实例。`persist_empty` 表示无人时保留大厅房间，不表示普通房间已实现跨服务重启的数据库持久化。

## 创建和入房

玩家创建和加入房间都校验匹配队列、已分配对局、正在组桌、当前对局及已有房间成员身份。没有本地房间缓存，也不能同时占用第二个房间。赛事与基地继续使用原有场馆状态、报名和创建权限规则。

管理员创建沿用已有的空房工厂和各玩法校验器。房主初始为 0，第一个入座的真人成为房主。普通管理员房间与赛事、基地房间允许保留空房；普通玩家自建房在没有真人成员后解散。机器人不能独自维持普通玩家的大厅房间。

同一账号已经在目标房间时，重复加入恢复现有成员身份，不新增座位，也不会因为房间满员而拒绝本人的恢复请求。新成员仍需通过密码、人数、场馆权限和对局状态校验。已完成或取消的复式配对不能通过重新加入开始新比赛；管理端关闭中的房间禁止加入和开局。

## 开局和结算

开局检查准备、座位和队伍版本，登记对局身份，再锁定需要固定阵容的房间。川麻双打在对局中拒绝退房以保留阵容；客户端收到拒绝时仍须保留成员身份。

对局结束统一通过 `cleanup_game_state_complete` 停止任务、清理玩家和房间索引、处理观战及匹配关联，然后调用 `finish_custom_game_room`。只有房间实例和关联对局都相符，才能解锁该房间，避免迟到的清理影响下一场。

结算后的房间会清除准备状态，更新复式进度，移除已经断开的真人座位和个人房间设置，再同步房主。如果已经没有真人，普通玩家房间解散；允许保留的房间清空机器人和房主，继续等待入座。有在线成员时保留房间，房主离线则交给剩余真人。

排位匹配对局不存放在大厅 `rooms` 中，不出现在房间管理列表。其结束和强制结束仍归现有「对局管理」及匹配系统负责。

## 断线与重新登录

旧问题存在两个相连的缺口：双打锁定期间断线退房被拒绝，随后对局清理没有移除这些离线座位；完全退出后重新登录又没有恢复房间缓存和主动同步，点击满员房间会再次被人数检查挡住。

现在断线先标记该连接正在断开。即使它还暂存在连接映射中，也不会被结算清理认定为在线。缓存缺少房间号时按成员名单补查。活动对局仍按原有策略保留必要座位；结束解锁后清除离线成员。旧连接的迟到断开事件不能清理同一账号的新连接。

登录成功后，服务端从成员名单恢复 `current_room_id`；Unity 普通登录主动发送 `room/sync_my_room`。自动重连继续使用已有同步阶段，避免重复发起。

| 同步结果 | 客户端行为 |
| --- | --- |
| `room/refresh_room_info` 且仍为成员 | 恢复房间号及房间页面；旧对局已结束也不再抹掉已恢复的房间 |
| `room/sync_not_in_room` | 清理旧房间身份，停留或返回大厅 |
| 退房请求被拒绝 | 保留成员身份，继续接收房间更新 |
| 退房或解散确认成功 | 清理成员身份；带旧实例号的迟到确认不能清除新房间 |

如果房主断线期间房间已经解散，重新登录应回到大厅，不再试图恢复该房间。若房间还有其他在线成员，原房主可以重新加入空座，但房主身份可能已经转移。

## Web 房间管理

入口位于「对局管理」上方，沿用现有后台布局及房间创建面板。

- 列表显示房间号、名称、所属赛事或基地、玩法、房主、玩家在线情况、人数、运行状态及复式开闭室。可搜索、筛选等待中或对局中及无人在线，按需开启 5 秒刷新。
- 创建可选普通房间或有效赛事、基地，复用各玩法配置。赛事复式使用原有开闭室与牌山创建流程，按组计数；创建中途失败会报告实际已创建数量，不自动重复创建。
- 关闭等待房间会解散房间并通知成员。关闭正在进行的房间先结束关联对局、释放任务和索引，再解散房间。关闭复式任一桌会处理整组开闭室，保存配对取消或已有完成状态。
- 正在自动组桌的房间暂不允许关闭；关闭开始时封住入房和开局。提交携带列表中的 `instance_id`，旧列表不能误关同号的新实例。
- 创建、关闭需要操作原因，记录后台审计。普通预建空房可通过此入口主动关闭；不能仅凭「无人在线」批量判断为死房间。

## 接口和访问控制

| Web 管理接口 | 用途 |
| --- | --- |
| `GET /api/admin/room-control` | 读取大厅房间快照及场馆名称 |
| `GET /api/admin/room-control/venues` | 有效赛事、基地选项 |
| `POST /api/admin/room-control/create` | 创建普通房间或委托现有赛事创建流程 |
| `POST /api/admin/room-control/:roomId/close` | 校验实例后关闭房间或整组复式 |
| `GET /api/admin/event-applications/pending-counts` | 读取办赛、基地各自的待审核数量 |

以上入口在平台管理员认证中间件之后注册，普通玩家 token 和未登录请求不能访问。操作者身份取自认证结果。管理列表采用字段白名单，不返回房间密码、牌山密钥或随机种子。

新增 Python `/admin/rooms` 系列接口仅接受本机 Node 代理调用，同时验证 30 秒内、绑定请求方法、路径和请求体的 HMAC 签名。回环地址不单独作为身份凭据，防止公开反向代理转发的匿名请求冒充本机管理端。签名复用现有网站与游戏服共同配置的 `PLAYER_JWT_SECRET`，Node 缺省沿用 `ADMIN_JWT_SECRET`，Python 对应 `Config.player_jwt_secret`；没有可用密钥时拒绝访问。

## 红色申请气泡

「办赛申请」「基地申请」分别显示 `event_applications` 中对应种类且状态为 `pending` 的数量。零条隐藏，超过 99 条显示 99+。打开页面、切换后台页面、窗口重新获得焦点及可见时每 30 秒刷新；审核完成后立即刷新。隐藏页面停止周期请求，退出登录清空计数并丢弃旧请求响应。短暂请求失败保留上一次确认的数量，下一次刷新重试。

气泡代表待处理申请数量。查看页面不会将未处理申请消除，也不会把申请的修改申请混入新办赛或基地申请数量。

## 验证和发布边界

服务端回归覆盖完整房间测试集，以及对局生命周期、会话注册、双打全员断线、冷登录满房恢复、房主离线后重新加入、管理端关闭运行对局与双桌复式、房间号复用及代理认证。Node 测试覆盖管理员权限、申请计数、批量创建部分失败、审计、已有赛事创建流程和请求签名。

浏览器在本地验证了血战和血流双打房间的创建、筛选、关闭，以及两类测试申请审核后的气泡更新。Unity 编辑器使用实际登录回调和受控同步响应，验证保留房间与房间已删除两条路径。构建验证不等于已发布；Android 真机后台恢复仍需设备验收。此次改动不部署生产环境，也不主动批量清理线上房间。
