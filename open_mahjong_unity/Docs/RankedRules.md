# 四规则段位与 Elo 匹配

固定界面保存在 `Assets/Scenes/MainScene.unity`，在原 MainCanvas、Header、玩家资料和匹配页上增量扩展。示例工程不是主项目依赖，也不参与运行时加载。

## 当前开放规则

| 规则 | 评分 | 匹配入口 |
| --- | --- | --- |
| 国标麻将 | 原级段制、PT，同时保存独立 Elo R | 初级、中级、高级、MCRPL，各有东风／半庄／全庄，12 个队列 |
| 立直麻将 | 级段制、PT，同时保存独立 Elo R | 初级、中级、高级，各有东风／半庄，6 个队列 |
| 青雀 | Elo R | 全庄战，1 个队列 |
| 川麻血战 | Elo R | 全庄战（16 局），1 个队列 |

四种规则独立记分，初始 R 为 1500。国标段位继续以原 `rank_data.guobiao_rank/guobiao_score` 为准，包含管理员既有赋分；不会从示例工程导入任何玩家数据。立直复用现有 PT 表和升降级算法，准入条件读取立直自身段位。原资格授权和国标 MCRPL 规则保留。

Elo 按最终名次做四人两两比较，K = 32，对三个对手取平均；并列按平局计算。结果保留两位小数，末位吸收舍入差，使四人变动之和为零。所有场次按入队顺序组桌，同一队列满四人立即创建对局，不按 R 值筛选，也不设置匹配成功倒计时。国标初级场开启番数提示，立直初级场仅开启枚数提示；两者的中高级场仍不提供这两种提示。

每日对局量的 100 局说明用于解释制度选择。规则不会因为某天跨过阈值就自动切换制度；将来由平台公布规则调整和赋分方案，现有评分保留。其他娱乐或开发中规则仍可自定义游玩，不开放排位入口。

预期映射采用 `E = 1 / (1 + 10^((对手 R - 自己 R) / 2000))`。每位对手的实际结果 `S` 为名次胜出 1、并列 0.5、落后 0；`R 变化 = (32 / 3) × Σ(S - E)`。相差 600 R 的两两名次胜出预期约为 66.61%。不迁移或重置这套新设计的四人规则评分。

## 交互

- 数据页原规则按钮替换为四选项 TMP_Dropdown。一次选择同步请求该规则的最近匹配对局和排行榜。段位榜按段位、PT 排序并显示 R；Elo 榜按 R 排序。加载、空数据、失败、15 秒超时和刷新分别处理。每次请求带唯一标识，迟到回复不能覆盖新选择。
- 主菜单玩家卡片和玩家资料顶部循环切换国标、立直、青雀、川麻。查看排行榜玩家时，资料默认使用该榜的规则。段位制显示 PT 进度和 R，Elo 显示 R 与场数。
- 玩家资料的天梯统计提供四个规则按钮，自定义对局保留原有其他规则选择。立直、青雀的匹配和自定义统计分别缓存，番种统计也分别汇总。
- 匹配页提供四个规则标签，点击场次即加入，再次点击取消。跨规则切换保留真实队列，最多同时等待四场。底部条目保留规则名称，避免跨规则场次混淆；取消全部、匹配成功锁定、断线清理沿用现有流程。
- 匹配页和资料页提供已烘焙的“段位机制说明”。Elo 卡片的感叹号打开 Elo 说明。匹配页 R 值旁的 `?` 在鼠标悬停或键盘选中时展示完整算法，移开、失焦或离开面板时隐藏；固定问号和提示框都已烘焙进场景。
- 服务端结算返回规则、结算前后段位／PT／R 和场数；客户端按用户 ID 更新对应规则评分。国标、立直显示升降段动画和 R 变化，青雀、川麻显示 Elo 结算，不显示 PT 进度。

## 场景与字体维护

`Tools/Mahjong/Main Scene/Update Elo Help` 仅增量更新问号、算法提示和 Elo 说明，不重建其他主菜单内容。`RankedEloHelp` 只控制已序列化提示框的显隐。

`Tools/Mahjong/Main Scene/Update Ranked Queue Options` 可增量更新已有场景的全庄入口、说明与提示文案，并保留其他面板样式。`Tools/Mahjong/Main Scene/Bake Ranked Rules UI` 是完整编辑器维护工具。只在编辑模式、主场景中运行；保存下拉模板、四套规则页、20 个匹配卡片、说明弹窗、空状态文本、按钮事件与序列化引用，并更新排行榜条目预制体。不会在游戏启动时克隆 MainCanvas 或用代码临时生成固定页面。

固定字号、颜色、锚点和宽度在场景或预制体上维护。主项目现有 Alibaba 静态 SDF 字体覆盖新增中文、英文和数字；原段位描边字体保留。结算使用“至”表达 R 的前后变化，避免原静态图集未包含的箭头字符。排行榜 PT／R 列以右侧为锚点，自动字号控制在烘焙范围内。

随服务器数据变化的排行榜、对局记录、统计明细继续使用原有列表预制体生成；下拉列表打开时由 TMP_Dropdown 实例化其已烘焙模板。这些是正常的数据与控件生命周期。

## 服务端与兼容性

需要同时更新 `open_mahjong_server` 并重启。启动数据库初始化会增量创建 `rule_ratings` 和 `rating_settlements`，不删除或重置原表。一次四人评分结算在同一事务完成，按玩家 ID 排序加锁；游戏 ID 为幂等键，重复投递不会重复扣加分，失败会回滚四名玩家。

国标原 12 个队列 ID 保留。其他规则使用 `riichi_<tier>_<mode>`、`qingque_elo_quanzhuang`、`sichuan_elo_xuezhan`。登录、资料和结算保留旧国标字段，并增加规则评分数据。数据请求增加 `rule` 和 `data_request_id`，回复原样携带。川麻保留 `sichuan_elo_xuezhan` 协议标识，但局制为全庄、`game_round=4`。客户端和服务端应一并更新。

## 验证入口

- Python：在服务端目录执行 `python -m pytest server/match server/database server/gamestate/game_guobiao server/gamestate/game_riichi server/gamestate/game_mmcr server/gamestate/game_sichuan`。数据库集成测试需设置 `RATING_TEST_DATABASE_URL`、`INVENTORY_TEST_DATABASE_URL`、`TITLES_TEST_DATABASE_URL`，测试使用随机隔离 schema 并清理，禁止指向非测试环境。
- Unity：`RankedRulesUiBaker.Validate()` 检查四页、20 个唯一队列和序列化引用；`MainSceneUiBaker.Validate(scene)` 保留原固定 UI 验证；`RankedRulesBuildValidation.ValidateFonts()` 检查现有静态字库。
- `RankedRulesRuntimeValidation` 仅在 Editor 或 Development Build 中编译，默认不运行。显式提供 `--verify-ranked-rules <输出目录> <隔离的回环 WebSocket 地址>` 才启动；不会向正常游戏服务注入测试身份。测试原生 UI 射线点击、真实入退队、规则数据响应、段位准入、游客拦截、结算、字体和截图。固定业务 UI 不依赖该探针。
- 构建工具输出和验证截图只保存到本机 `.om_workspace/`，不进入项目资源或正式数据。
