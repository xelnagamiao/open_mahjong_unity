# 多规则段位与 Elo 匹配

固定界面保存在 `Assets/Scenes/MainScene.unity`，在原 MainCanvas、Header、玩家资料和匹配页上增量扩展。示例工程不是主项目依赖，也不参与运行时加载。

## 当前开放规则

| 规则 | 评分 | 匹配入口 |
| --- | --- | --- |
| 国标麻将 | 原级段制、PT | 初级、中级、高级、MCRPL，各有东风／半庄／全庄，12 个队列 |
| 立直麻将 | M 规比赛分驱动的争一 PT | 初级、中级、高级，各有东风／半庄，6 个队列 |
| 青雀 | Elo R | 全庄战，1 个队列 |
| 川麻血战 | Elo R | 全庄战（16 局），1 个队列 |
| 立直三麻 | 独立级段制、PT | 初级、中级、高级，各有东风／半庄，6 个队列 |
| 川麻血流换三张 | 独立 Elo R | 全庄战（16 局），1 个队列 |

六种规则独立记分。国标、四人及三人立直只结算段位和 PT；青雀、川麻血战、血流换三张初始 R 为 1500。国标段位继续以原 `rank_data.guobiao_rank/guobiao_score` 为准，包含管理员既有赋分。四人立直保留段位名称和升降级门槛，PT 改为 `q × (k × M - C)`：M 为 M 规比赛分，半庄 q=1、东风 q=0.7；初级／中级／高级 k=0.3／0.6／1，C 是按段位和场次设置的统一扣分。准入条件读取立直自身段位。原资格授权和国标 MCRPL 规则保留。

血流换三张固定使用 `sichuan/xueliu_exchange` 子规则、`sichuan_xueliu_exchange_elo_quanzhuang` 队列和 `sichuan_xueliu_exchange` 评分池。其 Elo、排行榜、匹配统计及近期战绩独立于血战，旧版子规则为空的川麻匹配记录仍归血战。完整规则见 [换三张设计稿](../../open_mahjong_server/docs/sichuan-xueliu-exchange-design.md)。

三人立直按最终顺位计算 PT：东风初级、中级、高级的第一名分别 +30、+50、+70，第二名均为 0，第三名对应 −30、−50、−70；半庄乘 1.5。使用独立 `riichi_sanma` 评分池和 `sanma_tenhou` 玩法预设，同点按起始座次排序。完整说明见 [三人立直段位计分](../../open_mahjong_server/docs/riichi-sanma-rank-progression.md)。

所有场次按入队顺序组桌，三人立直满三人、其他队列满四人立即创建对局，不按 R 值筛选，也不设置匹配成功倒计时。国标初级场开启番数提示，立直初级场仅开启枚数提示；两者的中高级场仍不提供这两种提示。

每日对局量的 100 局说明用于解释制度选择。规则不会因为某天跨过阈值就自动切换制度；将来由平台公布规则调整和赋分方案，现有评分保留。其他娱乐或开发中规则仍可自定义游玩，不开放排位入口。

Elo 使用 K=32、2400 分母和桌均 R 低于 1500 时的保护奖励，详见 [平台评分](../../open_mahjong_server/docs/platform-ratings.md)。四人立直匹配房采用 `mleague` 预设，比赛分为 `(终局点数 - 30000)/1000 + [50,10,-10,-30]`，一位奖励已含头名奖。同点分摊顺位奖励，供托余差不拆开共享名次。完整配表见 [立直段位计分](../../open_mahjong_server/docs/riichi-rank-progression.md)。已有段位与 PT 保留，十段固定 100/100 PT。

## 交互

- 数据页提供六选项 TMP_Dropdown。一次选择同步请求该规则的最近匹配对局和排行榜。段位榜按段位、PT 排序；Elo 榜按 R 排序。加载、空数据、失败、15 秒超时和刷新分别处理。每次请求带唯一标识，迟到回复不能覆盖新选择。
- 主菜单玩家卡片和玩家资料顶部循环切换六种规则。查看排行榜玩家时，资料默认使用该榜的规则。段位制显示 PT 进度，Elo 显示 R 与场数。
- 玩家资料的天梯与自定义统计共用四个主按钮：国标麻将、立直麻将、青雀、川麻血战。右侧“其他规则”下拉框在天梯中提供“立直(三人)”和川麻血流换三张；自定义中额外提供“国标(三人)”、其余已注册规则、独立的广东麻将和广东麻将（推倒和）、上海麻将（敲麻）和上海麻将（清混碰），南雀固定放在最后。地区名称使用“××麻将”；虹雀、红中麻将、自由模式和古典麻将使用各自本名。三人和四人立直的匹配统计、役种统计及近期战绩独立汇总。
- 匹配页使用四个外层规则标签，立直与川麻在内部切换玩法，布局见下节。点击场次即加入，再次点击取消。跨规则或玩法切换保留真实队列，最多同时等待四场。底部条目保留完整玩法名称，避免跨玩法场次混淆；取消全部、匹配成功锁定、断线清理沿用现有流程。
- 匹配页提供已烘焙的“段位机制说明”，玩家资料页使用“其他规则”下拉框。Elo 卡片的感叹号打开 Elo 说明。匹配页 R 值旁的 `?` 在鼠标悬停或键盘选中时展示完整算法，移开、失焦或离开面板时隐藏；固定问号和提示框都已烘焙进场景。
- 服务端结算返回规则、对应评分变动和场数；客户端按用户 ID 更新对应规则评分。国标、立直显示升降段动画；四人立直额外显示 M、k、C 和 q，三人立直显示独立顺位 PT。青雀、川麻显示 Elo 结算。三人立直的近期走势仅显示第一至第三名，四人走势仍显示四个顺位。

## 匹配页设计

| 外层入口 | 内部切换 | 首次进入 | 对应评分 |
| --- | --- | --- | --- |
| 国标麻将 | 无 | 国标 | 国标段位、PT |
| 立直麻将 | 四人／三人 | 四人 | 分别显示四人或三人的段位、PT |
| 青雀 | 无 | 青雀 | 青雀 Elo |
| 川麻 | 血战到底／血流换三张 | 血战到底 | 分别显示血战或血流换三张的 Elo |

页面上方的工具行右对齐“段位机制说明”，单独占位，避免覆盖评分。其下从上到下排列为“外层规则与评分摘要 → 内部玩法切换 → 场次卡片 → 已加入的匹配队列”。外层始终只显示四个入口。立直与川麻选中时，在场次卡片上方展示两个玩法按钮；国标与青雀隐藏这一行，不占额外空白。评分摘要、问号说明与场次卡片同时跟随当前玩法更新。

外层标签的在线人数合计同类玩法，内部按钮分别显示各玩法人数。收到完整的零人数数据时显示 `0`，尚未收到或缺少所需玩法数据时显示 `—`。人数更新不改变当前玩法。

返回立直或川麻时，恢复本次运行中该入口上次选择的玩法；关闭再打开匹配面板也保留该选择。新一次运行默认四人立直、血战到底。切换仅改变展示页，不加入或退出队列，血战与血流、四人与三人仍可同时排队，并受原有四场上限约束。每张队列条目保留完整玩法名，匹配成功进入其实际对应玩法。

视觉沿用现有浅灰面板、选中底色与场次卡片。外层四个标签等宽，右侧扩大评分摘要空间；内部按钮采用同一组选中样式，字号不低于 20。布局从上方对齐，内部行展开或收起时，外层导航与评分摘要的位置保持固定。场景参考尺寸为外层行高 70、内部行高 52，内层按钮宽 200。新增固定控件烘焙进主场景，运行时仅更新文字、人数和显隐。

所有 Elo 卡片的“Elo 匹配”标题明确采用 Alibaba 常规字体及其原始材质，包含可用与受限两个内容状态，避免继承段位卡片的特殊字形。国标与立直原有段位标题样式保留。内部切换只归并匹配入口，资料、排行榜和结算仍按六个独立评分池查询。

## 场景与字体维护

`Tools/Mahjong/Main Scene/Update Ranked Rule Groups` 增量维护匹配页四个外层入口、两个内部切换按钮、在线人数引用及 Elo 标题字体。只修改匹配面板，保留六套场次页及 27 个唯一队列。

`Tools/Mahjong/Main Scene/Update Elo Help` 仅增量更新问号、算法提示和 Elo 说明，不重建其他主菜单内容。`RankedEloHelp` 只控制已序列化提示框的显隐。

`Tools/Mahjong/Main Scene/Update Player Info Rule Picker` 仅增量维护玩家资料的四个主按钮与“其他规则”下拉框，保留原序列化引用。主按钮宽 120、间距 8，下拉框宽 240；标题保留左右内边距，长规则名使用限定字号范围。

`Tools/Mahjong/Main Scene/Update Riichi Ranked Descriptions` 维护立直专用计分表、段位扣分表、机制说明和结算明细，并保存主场景。固定表格使用原生 UI 预制体，国标表格与立直表格按规则切换；运行时不生成固定表格。

`Tools/Mahjong/Main Scene/Update Ranked Queue Options` 可增量更新已有场景的全庄入口、说明与提示文案，并保留其他面板样式。`Tools/Mahjong/Main Scene/Bake Ranked Rules UI` 是完整编辑器维护工具。只在编辑模式、主场景中运行；保存下拉模板、六套规则页、27 个匹配卡片、说明弹窗、空状态文本、按钮事件与序列化引用，并更新排行榜条目预制体。不会在游戏启动时克隆 MainCanvas 或用代码临时生成固定页面。

固定字号、颜色、锚点和宽度在场景或预制体上维护。主项目现有 Alibaba 静态 SDF 字体覆盖新增中文、英文和数字；原段位描边字体保留。结算使用“至”表达 R 的前后变化，避免原静态图集未包含的箭头字符。排行榜 PT／R 列以右侧为锚点，自动字号控制在烘焙范围内。

随服务器数据变化的排行榜、对局记录、统计明细继续使用原有列表预制体生成；下拉列表打开时由 TMP_Dropdown 实例化其已烘焙模板。这些是正常的数据与控件生命周期。

## 服务端与兼容性

需要同时更新 `open_mahjong_server` 并重启。启动数据库初始化会增量创建 `rule_ratings` 和 `rating_settlements`。四人立直新排位局在创建时固定 `riichi_mleague_pt_v1`，三人立直固定 `riichi_sanma_place_pt_v1`；切换前已开始的对局沿用旧算法，历史结算与现有 PT 保留。整桌三人或四人评分结算在同一事务完成，按玩家 ID 排序加锁；游戏 ID 为幂等键，重复投递不会重复扣加分，失败会回滚整桌玩家。

国标原 12 个队列 ID 保留。其他规则使用 `riichi_<tier>_<mode>`、`riichi_sanma_<tier>_<mode>`、`qingque_elo_quanzhuang`、`sichuan_elo_xuezhan` 和 `sichuan_xueliu_exchange_elo_quanzhuang`。登录、资料和结算保留旧国标字段，并增加规则评分数据。数据请求增加 `rule` 和 `data_request_id`，回复原样携带。川麻保留 `sichuan_elo_xuezhan` 协议标识，但局制为全庄、`game_round=4`。客户端和服务端应一并更新。

玩家资料的其余自定义玩法通过 `data/get_rule_stats` 查询，传入统计标识、实际房间规则、子规则、人数与请求标识，回复使用现有 `rule_stats` 结构并回显 `data_request_id`。同一大类下的三人场、广东两种玩法及南雀分别筛选历史样本；切换规则后迟到的回复只更新对应缓存。

## 验证入口

- Python：在服务端目录执行 `python -m pytest server/match server/database server/gamestate/game_guobiao server/gamestate/game_riichi server/gamestate/game_mmcr server/gamestate/game_sichuan`。数据库集成测试需设置 `RATING_TEST_DATABASE_URL`、`INVENTORY_TEST_DATABASE_URL`、`TITLES_TEST_DATABASE_URL`，测试使用随机隔离 schema 并清理，禁止指向非测试环境。
- Unity：`RankedRulesUiBaker.Validate()` 检查四个外层入口、两个内部切换按钮、六页、27 个唯一队列、序列化引用及 Elo 标题字体；`MainSceneUiBaker.Validate(scene)` 保留原固定 UI 验证；`RankedRulesBuildValidation.ValidateFonts()` 检查现有静态字库。
- 三人立直：`RiichiSanmaRankValidation.Run()` 检查独立评分、六个场次、资料统计和已保存的主场景引用；`RiichiSanmaRankClientValidation` 在开发构建显式传入 `--verify-sanma-rank <输出目录> <回环 WebSocket 地址> <测试UID>` 时验证真实三客户端匹配、重连、终局和段位弹窗。正常启动不运行该验证。
- `RankedRulesRuntimeValidation` 仅在 Editor 或 Development Build 中编译，默认不运行。显式提供 `--verify-ranked-rules <输出目录> <隔离的回环 WebSocket 地址>` 才启动；不会向正常游戏服务注入测试身份。测试原生 UI 射线点击、真实入退队、规则数据响应、段位准入、游客拦截、结算、字体和截图。固定业务 UI 不依赖该探针。
- 构建工具输出和验证截图只保存到本机 `.om_workspace/`，不进入项目资源或正式数据。
