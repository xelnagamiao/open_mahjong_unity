# 青雀局均素点 Elo 与无固定时限匹配

版本：`qingque_mean_points_v2`。本方案沿用青雀现有独立 Elo 账户。新开的全庄匹配和无固定时限匹配都使用本算法；正常启动不改写历史。另提供[一次性历史重算脚本](qingque-elo-rebuild.md)，可在维护窗口把全部青雀匹配历史统一为新算法。

## 1. 目标与口径

- 按净素点表现计算 Elo，不再把成绩压缩为第一至第四名。净赢更多，积分收益更大；不设置单场涨跌硬上限。
- 保留初始 1500 分、两位小数、青雀独立积分池，以及现有低分桌保护。
- 无固定时限指不预设整场局数；出牌、操作和断线托管计时照常生效。
- 任一玩家可申请本局结束后终止整场，其他三人无需同意。本局必须完成，随后四人统一结算，不替换玩家继续计分。
- 局间申请结束，不再发下一局。未冻结结算时可以撤回；结算冻结后不得撤回。

“素点”使用服务端青雀玩家累计 `score`：起点为 0，包含各个已完成局的全部合法点数收支。四人合计必须为 0。不是和牌番数、比赛名次分、PT 或最终名次。

记实际完成局数为 N，累计净素点为 Y，局均素点 A=Y/N。牌谱中已经写入 `end` 的局才计入 N，流局也计入；未完成局、重连次数、准备次数均不计入。N=0 不结算、不增加场数。

## 2. 参考仓库与取舍

参考 [mmcr14.online 的 ranking/service.cc](https://github.com/xelnagamiao/mmcr14.online/blob/9448ca0f5b29d625cbfbd5b038a8cbd52f3bba4a/backend/src/ranking/service.cc) 及同目录 `service.h`，固定审阅版本为 `9448ca0f5b29d625cbfbd5b038a8cbd52f3bba4a`。

参考实现以能力均值 μ、不确定度 τ 和局内波动 σ 更新表现，核心证据是 `Y − N × (μ自己 − μ桌均)`。能力评级、段位积分和展示等级并非同一量。

本项目采用其“局均净素点相对同桌实力预期的偏差”思想，使用固定先验权重；不照搬完整的不确定度、段位积分和升级系统。全部玩家在同一个更新前快照上计算，避免循环内更新影响后面的玩家。参数 32 和 1584 是为本项目 Elo 幅度设计的校准值，不是参考仓库原值，也不是已经通过历史数据拟合的结论。

## 3. 公式

R 为结算事务读取并锁定的更新前青雀 Elo，四人均值为 R̄。正常匹配期间用户被该场次占用，不能同时加入第二桌。结算采用事务时的最新账户快照，管理员调分等特殊改动也不会被旧快照覆盖。

```text
能力映射：μ = (R − 1500) / 32
预期局均：A_expected = (R − R̄) / 32
表现变化：Δbase = 32N / (N + 1584) × (A − A_expected)
                 = 32 / (N + 1584) × [Y − N × (R − R̄)/32]
```

1584 为先验证据权重，可对应等方差高斯模型的 σ²/τ²。若沿用参考的 σ=300，则 τ≈7.538；实际实现直接使用固定权重，不保存或逐场收缩个人 τ。这样成熟账号仍能持续反映表现。

实际局数的作用：同样局均下，多局的变动更大；相同总净素点下，多打流局不会重复放大奖励。短局也有收益或损失。连续大幅领先产生线性增长的 Elo，没有用 `tanh`、名次换算或裁剪掩盖高素点结果。

### 低分桌保护

保留现行保护结构和 2400 的预期分母，按实际局数缩放保护力度：

```text
T = max(0, 1500 − R̄)
K_effective = 3200N / (N + 1584)
Eij  = 1 / [1 + 10^((Rj − Ri)/2400)]
E'ij = 1 / [1 + 10^((Rj + T − Ri)/2400)]
bonus_i = K_effective/3 × Σj≠i (Eij − E'ij)
R_new = R_old + Δbase + bonus
```

指数计算限制在 [-16,16]，用于数值稳定，与 Elo 涨跌封顶无关。N=16 时 K_effective=32，低分保护与原 16 局 Elo 一致。桌均至少 1500 时无保护。没有个人保底分。

普通变化以“分”为整数精度，先向下取整，再按最大余数分配，余数相同时按稳定 user_id 排序，确保四人普通变化严格零和且不受座位/遍历顺序影响。保护奖励单独四舍五入到两位，因此低分桌总积分可以增加。

### 示例（四人初始均为 1500，无保护）

| 完成局数 | 净素点 Y | 局均 A | 普通 Elo 变化 |
|---:|---:|---:|---:|
| 1 | +300 | +300 | 约 +6.06 |
| 4 | +200 | +50 | 约 +4.03 |
| 16 | +800 | +50 | +16.00 |
| 16 | +1600 | +100 | +32.00 |
| 16 | +3200 | +200 | +64.00 |
| 32 | +1600 | +50 | 约 +31.68 |

16 局的整桌 `[+800,+200,−200,−800]` 对应 `[+16,+4,−4,−16]`，与原顺位法 `[+16,+5.33,−5.33,−16]` 量级相近，但第二、三名的素点差会真实影响结果。

强手对弱桌的预期更高。例如 `[2100,1500,1500,1500]` 的强手预期局均为 +14.0625；16 局净赢 800 时普通变化为 +11.50，而不是同分桌的 +16。强手小幅正素点也可能扣分，代表表现低于该桌实力预期。

## 4. 匹配入口与操作流程

| 项目 | 全庄 | 无固定时限 |
|---|---|---|
| 队列 | `qingque_elo_quanzhuang` | `qingque_elo_unlimited` |
| 实际局数 | 通常 16 局 | 完成当前局后按终止请求结束，可超过 16 局 |
| 牌谱/统计模式 | `4/4_rank` | `unlimited/4_rank` |
| Elo 账户 | 青雀 | 青雀，与全庄共用 |

沿用现有满四人即匹配和队列占用逻辑，新增入口不引入额外 Elo 分段匹配。

1. 玩家进入青雀页，选择“素点 Elo · 全庄战（16局）”或“素点 Elo · 无固定时限”。问号显示青雀专属算法，卡片说明解释实际局数与结束规则。
2. 行牌期间按“结束游戏”后，服务端记录该用户的结束意愿并广播。该用户仍属于本局，正常操作或托管，不能借此抹掉本局损失。
3. 结束请求按用户身份记录，换位不会转移请求。多人请求各自独立；一人撤回不撤销其他人的请求。
4. 和牌/流局完成后确定完整成绩；存在请求则冻结，不再进入下一局。局间准备时收到请求，会唤醒准备等待并在发牌前重新检查。
5. 最终结算界面显示 Elo 前后、净素点、完成局数、局均、普通变化和保护奖励。排行榜沿用青雀 Elo 降序；并列等既有排序规则保持原逻辑。战绩单独标识无固定时限。

## 5. 结算、断线与恢复

- 客户端只提交结束意愿，不提交计分用的 Y、N 或 Elo。
- 每一完整局结束后，将累计成绩和仅含完整局的牌谱保存到 `qingque_rating_sessions`。状态为 `open → pending → complete`。
- 正常结束先冻结 `pending`。原 `rating_settlements` 以场次幂等，锁住四个账户后统一更新；记录算法版本、输入、前后分数及拆分明细。
- 同场重试返回已保存结果；同一场次的新算法重试若证据不同则拒绝，不能偷偷回退到顺位法。
- 牌谱、参与者和逐局统计沿用现有同事务发布。评分与牌谱分两个事务：任何一处中断都会保留恢复依据。再次发布先查该评分场次的牌谱，避免“积分已写、牌谱待写”时重复加分或重复出谱。
- 数据库暂不可用时保留玩家场次占用并重试。恢复任务也可处理已经冻结但未完成的结算。
- 四人全部离线时，新素点评分对局由已有断线托管完成当前局后结束，不直接删除对局。单人离线沿用重连/托管；结束请求依然保留。
- 异常关闭采用最近已持久化的完整局，不能使用未结束局中的临时分数。服务器重启在接收连接前将遗留 `open` 冻结并恢复。零完成局不产生评分记录。
- 当前恢复流程针对现有单游戏服务实例。若将来改为多个同时运行的实例，启动恢复需增加房间租约/实例归属，不能直接全表接管 `open`。

## 6. 兼容与上线

新匹配配置明确写入 `rating_algorithm`；无固定时限仅接受新算法。无版本信息的旧全庄结算按旧顺位 Elo 处理，历史结果从已保存的结算记录读取。自定义青雀无固定时限继续不计 Elo。

数据库为增量建表，不清空玩家数据、不重置青雀积分。客户端与服务端需要配套更新，旧客户端没有新入口和结算明细。配置/匹配改动不改变青雀和牌规则，因此不需要因本功能改写麻将规则支持表。

历史 Elo 全量重算属于独立维护操作，其一次性脚本、说明和专用测试已移入维护归档，不随常规版本发布。实时结算仍兼容已保存的算法版本；正常启动不会重置积分或重写历史结算，原有备份和完成标记继续保留。

实现入口：`match/qingque_score_elo.py` 负责纯数学计算；`match/qingque_session.py` 负责完整局检查点与恢复；`database/rule_ratings.py` 负责原子账户结算；青雀状态机负责结束边界；Unity 的 MatchButton、RankedRules、UnlimitedRoundPanel 和 EndGamePanel 负责显示及操作。

## 7. 验收与后续校准

自动化覆盖：同分桌幅度、同素点不同名次、强弱桌预期、低分保护、无硬上限、流局局数、四人顺序置换、零和舍入、完整局结束与超过 16 局、局间终止、冻结后拒绝撤回、数据库并发幂等、异常恢复、牌谱发布失败重试及新旧版本兼容。Unity 检查实际烘焙卡片、帮助文案、匹配结束按钮和最终结算面板。

上线后用真实青雀完整局数据观察局均分布、单场变化分位数、不同 Elo 档的预期残差和短场退出频率，再决定是否调整 32 或 1584，并增加新算法版本。以后参数升级默认不回写历史，若需要再次统一，应另行设计版本化迁移。本次参数是可解释的初始校准，未声称已经过线上分布验证。

无硬上限保留大牌的影响，也会增加极端局的波动；固定权重不会完全消除对局拆分和主动择时结束的影响。任何提前结束都结算实际完成局，托管及场次占用用于防止直接逃分；多人串通刷分仍需要另行设计风控，不能宣称本公式本身已解决。
