# 麻将规则资料长期搜集与归档设计

> 状态：设计稿 v2（2026-07-21）  
> 目标：用多日、增量、可复查的方式搜集地方麻将、竞技规则和自制规则，记录讨论热度，总结规则特色，并按“来源链接 + 可核验文本片段”归档。  
> 原则：**先建规则地图，再深挖单项；事实与总结分离；热度与资料质量分离；主线完备后转搜分支。**

---

## 1. 最终要得到什么

资料库分为四层，不能只做一张链接表：

| 层 | 回答的问题 | 主要产物 |
|---|---|---|
| 规则目录 | 世界上有哪些规则，它们是什么关系？ | `catalog/rules.json` |
| 热度快照 | 哪些规则值得优先研究，哪些只在小圈子活跃？ | `heat/YYYY-MM-DD.json` |
| 单规则档案 | 规则怎么玩、从哪来、有哪些争议和分支？ | `<slug>/PROFILE.md`、`sources.json` |
| 原始证据 | 上述判断凭什么？原文在哪里？ | `<slug>/excerpts/`、`rulebooks/`、网页快照元数据 |

“收齐全网”无法被严格证明，因此项目不以链接数量作为完成标准，而以**关键问题是否被高质量、相互独立的来源覆盖**作为阶段完成标准。

## 2. 目录设计

```text
other/rule/
  RULE_RESEARCH_WORKFLOW.md       # 本设计与操作规范
  inclued_rule/                   # 项目已经采用/定稿的规则书（保留现名）
  MIL_rule/                       # 现有 MIL 资料
  Rescoure/                       # 历史原典（保留现名）
  research/
    _README.md                    # 当前进度和入口
    catalog/
      rules.json                  # 规则总表、分类、父子关系、研究状态
    heat/
      YYYY-MM-DD.json             # 热度采样快照；不覆盖历史数据
    _templates/                   # 新规则档案模板
    <slug>/
      META.md                     # 身份、别名、范围、状态、下一步
      PROFILE.md                  # 有引文编号的特色/历史/争议总结
      sources.json                # 来源登记簿；每个事实可追溯
      search-log.md               # 搜过什么、未找到什么、下次搜什么
      excerpts/
        <source-id>.md             # 长文本片段、上下文及定位信息
      rulebooks/                  # 允许保存的规则书原文件
      snapshots/                  # 必要时保存网页/PDF版本信息或快照
```

`open_mahjong_web/client/public/rule-research/` 是展示层副本，不是事实源。事实源始终在 `other/rule/research/`；只有用户要求发布时才同步。

## 3. 规则分类：允许一项多标签

不要强迫一项规则只进一个抽屉。总表使用以下维度：

- `family`：十三张、十六张、其他牌数、牌类衍生。
- `origin`：国家/地区/城市；网络社区；作者或组织。
- `governance`：官方竞技、平台规则、地方习惯、自制规则、历史规则。
- `scope`：主规则、地方分支、赛事分支、人数变体、计分变体、牌具变体。
- `players`：二人、三人、四人或可变。
- `status`：活跃、历史、实验、失传/残缺、身份待确认。
- `relation`：`parent`、`derived_from`、`alias_of`、`influenced_by`、`conflicts_with`。

名称相同不等于规则相同，名称不同也不等于规则不同。建档前先做“身份消歧”：别名、地区、年代、发布者、牌数、起和条件至少核对四项。

## 4. 总表字段

`catalog/rules.json` 每条至少包含：

```json
{
  "slug": "hongkong",
  "name_zh": "香港麻将",
  "names": ["香港麻雀", "清章", "Hong Kong Mahjong"],
  "family": ["13-tile"],
  "origin": ["HK"],
  "governance": ["local", "organized-competition"],
  "scope": ["mainline"],
  "players": [4],
  "parent": null,
  "status": "active",
  "research_state": "surveyed",
  "heat_band": "B",
  "completeness": 62,
  "last_researched": "2026-07-20",
  "next_action": "核验现行总例全文与历史沿革"
}
```

`research_state` 只允许：

1. `candidate`：只知道名字；
2. `identified`：身份和别名已消歧；
3. `surveyed`：有基础规则、历史、热度来源；
4. `deep-research`：正在补关键缺口；
5. `mainline-complete`：主线资料足够，转搜分支；
6. `frozen`：规则已定稿且近期无需复查；
7. `blocked`：来源失效、语言或身份问题导致暂时无法推进。

## 5. 来源登记：保留证据，不把模型总结冒充原文

现有 `sources.json` 的字段继续有效；新条目逐步增加以下字段：

```json
{
  "id": "stable-short-id",
  "url": "https://example.org/rules",
  "canonical_url": "https://example.org/rules",
  "title": "页面原题名",
  "publisher": "发布者或站点",
  "author": null,
  "published": "2024-05-01",
  "updated": null,
  "accessed": "2026-07-21",
  "type": "rulebook",
  "source_level": "primary",
  "lang": "zh-Hans",
  "applies_to": ["mainline", "competition"],
  "topics": ["setup", "scoring", "penalty"],
  "local_path": "rulebooks/example.pdf",
  "archive_url": null,
  "content_hash": null,
  "rights_note": "仅保存必要引文；原文件许可待确认",
  "quote": "逐字摘录，保留原语言",
  "quote_location": "第 4 页，第 2.1 条",
  "context": "此段适用的版本和上下文",
  "summary_zh": "研究者概括，明确与 quote 分离",
  "claims": ["claim-win-minimum-3-fan"],
  "reliability": "high",
  "status": "verified",
  "notes": null
}
```

约束：

- `quote` 必须是源中真实存在的文本；翻译放在 `summary_zh`，不能放进引号冒充原文。
- PDF 要记录页码/条款；论坛要记录楼层、作者和发帖时间；视频要记录时间码。
- 搜索结果摘要只能用于发现线索，不能作为最终证据。
- 动态页面、易删帖子应记录存档链接或快照信息；不能保存时至少记录访问日期。
- 相同内容的转载合并为一条证据链，不虚增独立来源数量。
- 长文只在 `sources.json` 放短引文，较长的必要片段放 `excerpts/<id>.md`。
- 保存全文或下载文件前检查版权/许可；默认保存必要片段、元数据和原链接，不默认镜像整站。

### 来源等级

| 等级 | 例子 | 用途 |
|---|---|---|
| A / primary | 协会规则书、作者原帖、赛事规程、历史原典 | 确定条款与版本 |
| B / strong-secondary | 学术论文、专业书、可靠媒体深度稿 | 历史和背景交叉验证 |
| C / community | 大型论坛长帖、规则百科、平台说明、教学站 | 找地方实践、争议和变体 |
| D / lead-only | 无出处转载、短视频口述、搜索摘要 | 仅作线索，不能独立定论 |

`reliability` 是对“该条信息能否支持指定主张”的判断，不是对整个网站贴标签。

## 6. 规则特色如何总结

`PROFILE.md` 使用统一骨架，便于横向比较：

1. 一句话定义及与近邻规则的边界；
2. 牌具和人数；
3. 开局、摸打、鸣牌、杠、和牌流程；
4. 和牌结构与特殊牌型；
5. 起和门槛、计分、支付、封顶；
6. 连庄、流局、包牌、犯规等局制；
7. 最具辨识度的 3–8 项机制；
8. 内部分支和桌规差异；
9. 历史沿革（把“有证据”与“传说”分开）；
10. 当前社群、平台、赛事和讨论焦点；
11. 已知矛盾、未知项和下一步。

每个事实句尾引用 `[source-id]`。遇到冲突不强行选边，写成“来源 A 规定……；来源 B 的某地区版本则……”并标明年代和适用范围。

推荐同时维护一个比较表：

| 规则 | 牌数/人数 | 起和 | 计分核心 | 标志机制 | 主要分支 | 热度 | 完备度 |
|---|---|---|---|---|---|---|---|

## 7. 讨论热度：做可重复的采样，不伪造精确排名

热度不是“规则好不好”，也不是搜索结果总数。搜索引擎命中数不稳定，只能当弱信号。每次热度快照记录**查询词、平台、时间窗、可见计数和采样日期**。

### 7.1 五个热度维度

| 维度 | 建议信号 | 权重 |
|---|---|---:|
| 搜索关注 | 多语言精确词的趋势/搜索可见度 | 20% |
| 内容产出 | 近 12 个月新帖、视频、文章数量 | 25% |
| 互动强度 | 播放、评论、回复、收藏的中位数或分位数 | 20% |
| 活跃生态 | 活跃平台、赛事、在线实现、固定社群 | 25% |
| 持续性 | 近 3 年是否持续出现新内容 | 10% |

每维按明确采样结果评 `0–5`，总分换算为 100。无法取得的数据填 `null`，不得填 0；同时给出 `confidence`（高/中/低）和覆盖的平台列表。

### 7.2 分层而非虚假的绝对名次

- A：跨平台、持续活跃，有赛事或大型在线生态；
- B：地区/语言圈内稳定活跃；
- C：小众但有持续讨论或维护者；
- D：零星、历史性或短期话题；
- U：证据不足，暂不评级。

自制规则可能总量很小但互动率很高，应额外记录 `community_intensity`，避免被大众规则的绝对量完全淹没。

### 7.3 快照最小格式

```json
{
  "sampled_at": "2026-07-21",
  "window": "rolling-12-months",
  "rule": "hongkong",
  "queries": ["\"香港麻将\" 规则", "\"Hong Kong Mahjong\" rules"],
  "platforms": [
    {"name": "bilibili", "query": "香港麻将", "visible_items": 50, "new_items": 12, "note": "只采前50条"}
  ],
  "scores": {"search": 3, "production": 3, "engagement": 2, "ecosystem": 4, "continuity": 4},
  "score_100": 64,
  "band": "B",
  "confidence": "medium",
  "limitations": "平台搜索存在个性化且只观察前50条"
}
```

热度应按月或按季度重采；日常研究不必每天刷新。不同日期的算法变更要写版本号，旧快照不回填。

## 8. 完备度与停止规则

完备度评估资料覆盖，不评估规则本身。建议满分 100：

| 模块 | 分值 | 达标条件示例 |
|---|---:|---|
| 身份与别名 | 5 | 已消歧，关系清楚 |
| 现行核心规则 | 25 | 有完整权威规则或多源重建 |
| 计分/役种 | 15 | 表格、例外、支付可核验 |
| 局制/罚则 | 10 | 连庄、流局、犯规等有覆盖 |
| 历史 | 10 | 至少两个独立来源，关键年代有依据 |
| 分支/桌规 | 10 | 主要分歧已列出适用范围 |
| 实际生态 | 10 | 平台/赛事/社群有当前证据 |
| 热度采样 | 5 | 有可复现快照和局限说明 |
| 来源质量 | 10 | 有一手来源、定位信息、链接检查 |

### 主线标记 `mainline-complete` 的硬条件

- 核心玩法、计分、局制均有 A 级来源，或至少两个相互独立的 B/C 来源可重建；
- 关键条款没有未解释的重大冲突；
- 版本、发布者和适用范围明确；
- 完备度建议达到 80，且“现行核心规则”不少于 22/25；
- 连续两轮新增搜索没有发现会改变主规则总结的重要信息。

达到后不是永远停止，而是改变队列：

- 主线仅做链接失效检查、版本更新和勘误；
- 优先搜二/三人、双打、特殊赛事、平台改版、地方桌规和历史前身；
- 国标麻将这类已定稿规则，主规则书只保留权威版本链，不再堆积重复教学文；
- 出现新版规则书、重大赛事改制或可信新史料时自动“解冻”。

残缺/失传规则不能因缺少完整规则书永远卡住。若已穷尽已知入口，应标为 `blocked`，列明搜索范围、残缺部分和最可信重建，不冒充完整规则。

## 9. 每个规则的搜索矩阵

一轮深搜按来源类型和语言并行展开：

| 方向 | 查询构造 |
|---|---|
| 身份 | 规则名 + 别名 / 地名 / 作者 / 平台名 |
| 完整规则 | 规则名 + 规则书/总例/章程/教程 + `filetype:pdf` |
| 计分细则 | 规则名 + 番种/台数/役/计分/封顶/包牌 |
| 历史 | 规则名 + 起源/沿革/旧制/方志/报刊/论文 |
| 分支 | 规则名 + 二人/三人/双打/赛事/竞赛规程/地方名 |
| 争议 | 规则名 + 怎么算/是否/争议/桌规/house rules |
| 实现 | 规则名 + 游戏/平台/开源/代码/模拟器 |
| 多语言 | 简繁体、方言写法、英文、日文及当地语言别名 |

推荐入口顺序：官方组织和作者主页 → 图书馆/档案/论文 → 赛事和游戏平台 → 专业规则站 → 论坛与社媒 → 转载聚合。论坛不是低价值来源：地方规则和自制规则往往只有社区证据，但必须保留帖子身份与上下文。

搜索日志不仅记“找到什么”，还要记：查询式、平台、查看结果深度、失败原因、失效链接、付费墙、待追踪人名/书名。这样第二天不会重复劳动，也能证明“已穷尽到什么程度”。

## 10. 每日增量工作流

### A. 用户下达任务

建议口令：

```text
按 other/rule/RULE_RESEARCH_WORKFLOW.md 深搜：<规则名>。
本轮重点：<规则书/历史/热度/分支/争议/全部>；
语言与地区：<可选>；搜索预算：<可选，例如2小时或30个有效来源>；
结束后更新档案和缺口，不发布到网页。
```

### B. 开始前

1. 查总表及别名，确认不是已有规则或分支；
2. 阅读该规则 `META.md`、`PROFILE.md`、`search-log.md`；
3. 检查是否 `mainline-complete/frozen`，据此避开重复主线材料；
4. 写明本轮要解决的 3–8 个问题。

### C. 搜集

1. 先找 A 级来源并建立版本链；
2. 再用多语言、旧称和邻近地区名扩展；
3. 讨论材料围绕具体缺口搜，不盲目堆链接；
4. 每条材料立即登记元数据、短引文和定位；
5. 对关键主张至少寻找一个独立交叉来源；
6. 下载前判断许可与长期价值，做去重和哈希。

### D. 收尾

1. 更新 `PROFILE.md`，事实附来源 ID；
2. 更新特色比较表和规则关系；
3. 重新评估完备度，但说明分数变化理由；
4. 更新 `search-log.md` 的已完成、失败和下一步；
5. 检查 JSON 可解析、ID 唯一、本地路径存在、URL 未重复；
6. 给用户报告：新增证据、改变了哪些认识、仍缺什么、是否建议继续主线。

单日任务允许“没有搜完”。宁可留下准确的缺口和下一步，也不为凑完整度输出无来源结论。

## 12. 工具和模型分工建议

不建议把长期资料库交给单一模型“一次搜完”。更稳妥的是：

- 广泛发现网页、PDF和多语言别名：使用带搜索、能打开原页面并提供引用的深度研究模型；
- X 上的即时讨论和作者动态：Grok 通常有入口优势，但它不是论坛、中文旧网页和权威规则书的替代品；
- 中文平台和登录后页面：使用已有登录状态的浏览器逐页核验；
- PDF/OCR、表格整理、去重、JSON校验和仓库写入：由能操作本地文件与脚本的编码代理完成；
- 关键结论：始终回到原始页面/PDF人工可复核的位置，不以任何模型的回答本身作为来源。

选择模型时优先看五点：能否给出可打开的原链接、能否读取 PDF、是否覆盖目标平台、长任务中是否保留检索轨迹、能否稳定输出结构化数据。Grok 可以作为社媒侦察员，但不应独立承担整个规则资料库。

## 13. 迁移现有香港麻将档案

现有 `research/hongkong/sources.json` 可继续使用，不需要重做。后续分批补齐：

1. 新建 `PROFILE.md` 和 `search-log.md`；
2. 把 `excerpt` 逐步拆成 `quote`、`quote_location`、`context`、`summary_zh`；
3. 补发布者、发布日期、来源等级、适用分支；
4. 建立总表条目和独立热度快照；
5. 核验 HKMA 总例全文后再决定是否标记 `mainline-complete`。
